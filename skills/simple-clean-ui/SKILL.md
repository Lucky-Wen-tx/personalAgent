# 简单优先的界面

## 输入
- 这个界面要让人完成的那一件事。连你都说不清就先问，不要靠加说明文字绕过去。
- 现有的页面、代码或截图（可选）。有就照着改，没有才从零设计。
- 不能动的东西：既有接口、路由、埋点、对外契约，以及用户已经形成的操作习惯。

## 步骤
1. **先砍目标。** 用一句话写清这个页面要完成什么；一句话写不下的，说明它该被拆开。并列的次要目的要么移走，要么删掉。
2. **再砍架构。** 层级、面板、步骤、入口数量，各想一遍能不能再少一档。同一件事只在一个地方出现；一屏能看完的不要分成几步。
3. **删掉三类解释物，一次只删一类**：标语式大标题（不传达信息的那种）、提示文字（占位符里的引导、帮助气泡、解释段落）、次要标签（重复的、能推断的、纯装饰的）。每删一类，回头看一眼页面还读不读得懂。
4. **删完读不懂，就改布局，不要折回去加文字。** 这是这套方法的支点：调相邻关系、对齐、分组、留白和顺序，让结构自己说话。验收标准是「不看文字也能看出这块在干什么」。
5. **三边同时受益才算好决定。** 同一个修改按三个视角各问一遍：
   - UX：少一次点击、少一处犹豫、少一句要读的话？
   - DX：少一层抽象、少一个参数、少一处重复，而且调用方没有变麻烦？
   - AX：界面能被程序读准并操作——语义化的元素、稳定的定位、明确的状态和错误。只能靠人眼判断的界面，对智能体等于不可用。
   只让一边变好的改动先放下。真走到两头冲突时，优先保住可访问名和 AX，这两样删了很难补回来。
6. **不弄坏任何东西。** 删之前确认没别处依赖它（引用、选择器、测试、埋点、文档）。删掉可见文字时，顺手检查无障碍名、`aria-label`、`title`、错误提示有没有跟着变空——要留的名字就用程序能读的方式补上，而不是把可见文字加回来。

## 输出格式
- 直接交付改好的界面：一个能打开的文件，或一段能替换进去的实现，样式脚本内联，不依赖构建。
- 不附设计说明。要交代取舍就在对话里一句话说清：删了什么、为什么敢删、哪里让了一步。

## 不要做
- 不要用文案补设计的洞。说明文字、提示气泡、「这里有…」的标签，都是布局没解决问题的证据。
- 不要为了「简单」删功能、删状态、删错误处理。简单是表面更少、内部更准，不是能力更弱。
- 不要用不可见或看不懂的方式省略：hover 才出现的操作、只有颜色的状态区分、无文字图标的按钮。
- 不要拿 AX 换观感：`div` 冒充按钮、随机 class 名、状态只写在颜色里、错误只弹一个 toast。
- 不要为了 DX 堆抽象：多一层包装、多一个配置项，只有在同时减轻三方负担时才成立。
- 不要靠重写整个页面来证明简单。一次改动小到能被读懂地 review，本身就是好改动。
- 范围外的请求（改产品定位、写品牌文案、重构信息架构到需要产品决策）停下来问，不要自己发明。
